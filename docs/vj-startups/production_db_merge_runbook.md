# Production Database Setup Runbook

This is the step-by-step procedure for standing up the shared production Postgres
database — Plane core + the `vj_*` Django apps + backend 2's problem/idea tables all
live in one database, one instance.

**This procedure was validated on 2026-09-21** by running it end-to-end against a
throwaway local Postgres database (`plane_deploytest`): `manage.py migrate` (148
tables), then the bootstrap SQL (0 errors), then confirming the resulting table set
exactly matches the known-working local dev database, and confirming the cross-service
foreign key from `problems.addedByEmail` genuinely enforces against Django's real
`users` table. Not a paper procedure — it's been run.

## Why this isn't just "run migrate and then prisma migrate deploy"

Investigated and confirmed directly against the local dev database on 2026-09-21:

- Backend 2's `prisma/migrations/` folder is **stale**. Its very first migration
  (`20260805141008_init`) still contains `CREATE TABLE "users"` and legacy
  `startups`/`projects`/`tasks`/`project_members`/`task_comments`/`startup_team_members`
  tables from before the schema was consolidated onto Plane's own database — none of
  those tables exist in the live, working local database. The most recent migration
  (`20260920020000_add_user_session_token`) alters that same legacy `users` table
  with a `sessionToken` column that also doesn't exist anywhere live (the real
  session/admin tokens live on Django's `vj_organization_member_profiles` table
  instead — confirmed via `information_schema.columns`).
- There is **no `_prisma_migrations` table** in the local database at all — `prisma
migrate` has never actually been run against it. The real schema was evidently
  applied by hand or via `prisma db push` early on, against tables Django hadn't
  created yet.
- Running `npx prisma migrate deploy` against a production database where Django's
  `migrate` already created the real `users` table would fail immediately
  (`relation "users" already exists`) on the very first migration. Running `npx
prisma db push` is worse: because `schema.prisma` still fully declares the `User`
  and `OrganizationMemberProfile` models (deliberately, for read access — see the
  comment at the top of `backend/prisma/schema.prisma`), `db push` diffs the _entire_
  schema including those two Django-owned tables, and Django's `users` table has
  ~35 columns Prisma's model doesn't know about. A diff-based push against that is
  exactly the kind of operation that can generate a destructive `DROP COLUMN` before
  you get a chance to reject it.

So: **do not run any `prisma migrate` or `prisma db push` command against production.**
Instead, apply [`sql/prod_bootstrap_backend2_tables.sql`](sql/prod_bootstrap_backend2_tables.sql)
directly — it was generated by reading backend 2's actual live, working schema
(not the stale migration files) and creating only the 23 tables backend 2 genuinely
still owns (confirmed against real usage in `backend/APIs/*.js`), with the `verified`
columns already folded in as native columns rather than a separate ALTER step.

## Step 0 — Backup, before anything else runs

If this is a **fresh** production database (no prior data), there's nothing to back
up — skip to Step 1. If there is existing production data (e.g. this environment has
been live before this merge):

```bash
# Full logical dump, schema + data, compressed. Run this from a machine that can
# reach the production Postgres instance.
pg_dump -h <PROD_HOST> -U <PROD_USER> -d <PROD_DB> -F c -f plane_prod_backup_$(date +%Y%m%d_%H%M%S).dump

# Verify the dump isn't empty/corrupt before trusting it
pg_restore -l plane_prod_backup_*.dump | head -20
```

Store this dump somewhere off the database host (S3, a laptop, wherever) before
proceeding. Do not run Step 1 until this file exists and you've confirmed
`pg_restore -l` lists real table names.

## Step 1 — Apply Django's migrations

Django owns migrations for every table it defines: Plane's own core tables, and every
`vj_*` table (`Startup`, `Wing`, `VJProjectExtension`, `VJIssueExtension`,
`OrganizationMemberProfile`, etc.).

```bash
cd apps/api
export DATABASE_URL="postgresql://<PROD_USER>:<PROD_PASSWORD>@<PROD_HOST>:5432/<PROD_DB>"
python manage.py migrate --no-input
```

Verify: this should create ~148 tables total (confirmed count from the validated
local run) if starting from empty. Check with:

```bash
python manage.py shell -c "
from django.db import connection
with connection.cursor() as c:
    c.execute(\"SELECT count(*) FROM information_schema.tables WHERE table_schema='public'\")
    print(c.fetchone())
"
```

## Step 2 — Apply backend 2's tables

```bash
psql "postgresql://<PROD_USER>:<PROD_PASSWORD>@<PROD_HOST>:5432/<PROD_DB>" \
  -f docs/vj-startups/sql/prod_bootstrap_backend2_tables.sql
```

This runs inside a single transaction (`BEGIN`/`COMMIT` are in the file) — if any
statement fails, nothing is applied. Expected result: 23 new tables (`problems` + 6
child tables, `ideas` + 9 child tables, `questionnaire_*` x4, `announcements`,
`stage_notifications`), all foreign keys resolving cleanly against the `users` table
Step 1 already created. Verified by the 2026-09-21 test run: table count went from
148 (Django only) to 171 after the bootstrap, and back to exactly 125 after the
rollback script below (148 − 23), then cleanly re-applied — round-trips with no
residue.

If this step fails with `relation "users" does not exist`, Step 1 didn't run or ran
against a different database — stop and check `DATABASE_URL` before retrying.

## Step 3 — Seed the initial Wings + workspace structure

Only needed on a genuinely fresh instance (skip if wings/workspace already exist from
a prior deploy):

```bash
cd apps/api
python manage.py seed_vj_startups
```

## Step 4 — Backfill Cycles/Modules/Views on existing projects

New projects get `module_view`/`cycle_view`/`issue_views_view=True` automatically at
creation time (`OnboardingService`), but any project provisioned before that fix
landed needs a backfill. Safe to run even if there's nothing to backfill (no-ops
cleanly, confirmed by testing):

```bash
cd apps/api
python manage.py backfill_project_features --dry-run   # review what it would change
python manage.py backfill_project_features              # apply
```

## Step 5 — Configure the two Google OAuth integrations

See `production_env_checklist.md` section 1 — Plane's own team login is configured
via the Instance Admin panel UI (or seeded once from `GOOGLE_CLIENT_ID`/`_SECRET` env
vars on first `configure_instance` run), and backend 2's public-site login uses its
own, separate `GOOGLE_CLIENT_ID` in its own `.env`. Do this after Step 1 completes
(the admin panel needs the `InstanceConfiguration` table to exist).

There is no longer a Step 6. Earlier versions of this runbook had you log into
the production admin panel once to generate a `publicAdminToken` and copy it into
`VJ_MICROSERVICE_ADMIN_TOKEN`, with a 30-day expiry to track and rotate forever
after. As of 2026-09-21 that's gone: the admin proxy forwards the real acting
admin's identity, authenticated by `PUBLIC_SITE_INTERNAL_TOKEN` (which Step 1's
env setup already required) instead of one static personal token. Nothing to do
here beyond what the env checklist already covers.

## Rollback plan

**If Step 1 (Django migrate) fails partway through:** Django migrations run inside
their own transactions per-app; a failed migration doesn't leave the schema in a
committed broken state for that app, but apps that already migrated successfully
stay migrated. Options, in order of preference:

1. Fix the underlying issue (usually a missing extension or permission) and re-run
   `migrate` — it's idempotent, already-applied migrations are skipped.
2. If truly stuck and this is a fresh database: `DROP DATABASE`, recreate, start
   Step 1 over — nothing was lost since Step 0's backup (if any) is untouched.
3. If this was an existing production database with data: `pg_restore` the Step 0
   backup into a fresh database, point traffic back at it, investigate offline.

**If Step 2 (bootstrap SQL) fails:** the whole script is one transaction — a failure
mid-script means **zero** of the 23 tables were created (confirmed by the `BEGIN`/
`COMMIT` wrapping, and by directly testing the rollback/re-apply round-trip). Nothing
to roll back; fix the error (most likely cause: Step 1 wasn't actually run against
this database first) and re-run the whole script.

**If something is wrong after Step 2 completes and data has already been written
by users:** this is why Step 0's backup exists.

```bash
# Stop the application first so nothing writes during restore
pg_restore -h <PROD_HOST> -U <PROD_USER> -d <PROD_DB> --clean --if-exists plane_prod_backup_*.dump
```

`--clean --if-exists` drops existing objects before restoring, so this is safe to run
against the same database rather than needing a fresh one.

**If only the backend-2 tables need to be rolled back** (e.g. Step 2 was re-run
incorrectly after already succeeding once) and Django's tables are fine — this exact
script was tested end-to-end on 2026-09-21 (dropped all 23 tables cleanly, and the
bootstrap script re-applied afterward with zero errors):

```sql
BEGIN;
DROP TABLE IF EXISTS stage_notifications, announcements, questionnaire_criteria,
  questionnaire_recommendations, questionnaire_scores, questionnaire_responses,
  idea_links, idea_attachments, idea_reply_likes, idea_comment_replies,
  idea_comment_likes, idea_comments, idea_upvotes, idea_team_members,
  idea_collaborators, ideas, problem_reply_likes, problem_comment_replies,
  problem_comment_likes, problem_comments, problem_upvotes, problem_collaborators,
  problems CASCADE;
DROP TYPE IF EXISTS stage_type, questionnaire_status, access_level, worthiness_level;
COMMIT;
```

Then re-run Step 2 from the corrected script.
